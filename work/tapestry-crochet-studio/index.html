Case study 01 / 0→1 product

Tapestry Crochet Studio.

Turning a fragmented craft-production workflow into a local-first product system for artwork conversion, garment-aware pattern design, production and client operations.

RoleProduct Manager / Builder
DomainCreator tools + production
StatusActive development
ModelLocal-first → desktop → SaaS

01.00

The visible craft hid a production system.

I crochet custom tapestry pieces that turn people’s favourite anime, cartoons, photographs and other imagery into wearable or decorative objects.

The creative result is visible. The operational complexity is not. A single order can require image preparation, stitch-gauge correction, pattern cleanup, panel placement, yarn planning, row instructions, client approval, pricing, production tracking and export.

Product opportunity

Build one system around the end-to-end production job instead of treating image conversion as the whole problem.

02.00

“Turn an image into a chart” was not the real job.

A usable chart has to survive contact with yarn, gauge and garment construction. Crochet stitches are not automatically square. A face that looks correct on a digital grid can stretch on the finished piece. A design can collide with a neckline or armhole. A palette can look right on screen but fail against the yarn actually available.

The problem therefore crossed digital constraints, physical construction and the commercial workflow surrounding a custom order.

03.00

Six principles kept the product coherent.

01 / Crochet-aware

Gauge is structural.

Measured gauge controls physical proportions. Hook size alone is not a reliable product input.

02 / Editable

Human correction is core.

Generated output must remain editable because maker judgement is part of the workflow.

03 / Garment-aware

The garment is context.

Designs belong on front, back, sleeve and custom panels, not only an abstract grid.

04 / Source of truth

One grid, many outputs.

The same project state should power editing, instructions, production and export.

05 / Local-first

Production before cloud.

Core making and client artwork should work locally before cloud dependencies are introduced.

06 / Stage sophistication

Earn the SaaS layer.

Prove the single-user workflow before accounts, collaboration and subscriptions.

04.00

Build the irreversible truths first.

The foundation focused on artwork import, measured gauge, gauge-corrected rows, colour reduction, an editable grid, palette control, manual editing, bottom-up written instructions, local autosave and project export.

Explicitly deferred

Cloud accounts, subscriptions, teams and broad SaaS features. They were not allowed to distract from whether the production workflow itself worked.

05.00

The product boundary expanded with the real workflow.

The initial mental model was a single image becoming a single chart. Real use pushed the system toward multi-panel garments, yarn intelligence, production progress, exports and business operations.

Evolution path

Image → editable chart → garment-aware project → production workstation → yarn and order workflow → potential SaaS after validation.

06.00

Three decisions changed the product model.

Decision 01

Gauge is geometry, not metadata.

The engine uses actual stitch and row gauge plus source aspect to calculate physical proportions.

Decision 02

One project owns multiple panels.

Front, back, sleeves and custom panels can carry independent design, palette, grid and production state.

Decision 03

Flat preview beat weak 3D.

A truthful approval view served the client job better than an impressive but unreliable simulation.

07.00

Automation proposes. The maker remains in control.

Early background-removal approaches could remove the subject itself. The response was not to hide the failure behind stronger automation claims. The system moved toward conservative, recoverable controls such as tolerance, subject protection, smoothing, hole fill and largest-subject retention.

The broader principle is consistent: automated output should remain inspectable and editable.

08.00

Some defects create physical rework.

Row orientation is a correctness issue, not a cosmetic detail. Body panels are worked bottom to top, so row 1 must map to the bottom edge of the chart. Sleeve construction can use a different direction, so the product needs to communicate construction logic rather than force one convention everywhere.

Regression coverage therefore extends beyond UI behaviour into gauge correction, crop behaviour, colours, editing, garment placement, yarn matching, production progress, exports, business calculations and multi-panel persistence.

09.00

The job does not end when the chart is saved.

The product can represent customers and orders, create a quote, track approval, materials, payment and deadline states, and move a job toward delivery. Client-facing output separates visible line items from internal pricing mechanics.

Boundary decision

The app should own business workflow only where it needs to stay connected to design and production. It should not become a general accounting platform.

10.00

Desktop before SaaS.

Now

Strengthen production

Use the desktop workflow on real projects and resolve reliability and usability gaps.

Next

Validate externally

Design-partner testing, onboarding, measurable workflow improvements and repeat use.

Later

Add cloud deliberately

Accounts, encrypted sync, subscriptions, teams, shared libraries and analytics only after the core workflow is validated.

11.00

The next stage is validation, not feature volume.

This case study does not claim user growth, revenue, time savings or product-market fit that have not been measured. The next stage is to instrument the core workflow and test whether makers return.

01Activation: project → gauge → pattern/freestyle → valid panel → production/export.
02Time to production-ready panel versus the maker’s current workflow.
03Manual correction burden by generated pattern and correction type.
04Project save, migration and export success rates.
05Repeat project creation within 30 days.
06For business makers: quote-to-deposit conversion and lead-time visibility.
12.00

What this changed in how I think about product.

01 / Domain

Domain expertise changes the questions.

Generic image tooling misses the constraints that determine whether the finished physical object is correct.

02 / Recovery

Recoverability matters.

Automation is more useful when users can inspect, correct and continue than when it pretends to be infallible.

03 / Trade-off

Impressive is not the same as valuable.

Dropping a weak 3D direction in favour of flat approval views was a better product decision.

04 / Connection

The construction-tech connection is real.

Both domains force software to respect geometry, sequencing, materials, dependencies and physical execution.
