Tapestry Crochet Studio

Turning a fragmented craft-production workflow into a local-first product system for artwork conversion, garment-aware pattern design, production and client operations.

01 · Context

The visible craft hid a production system.

I crochet custom tapestry pieces that turn people's favourite anime, cartoons, photographs and other imagery into wearable or decorative objects.

The work can become a shirt, sweater, pillow, tote bag, blanket, wall hanging, rug or another custom piece. The creative result is visible. The operational complexity is not.

A single order can require image preparation, stitch-gauge correction, pattern cleanup, panel placement, yarn planning, row instructions, client approval, pricing, production tracking and export. I was moving between tools and manually reconciling information that belonged to the same project.

Product opportunity

Build one system around the end-to-end production job instead of treating image conversion as the whole problem.

02 · Problem

"Turn an image into a chart" was not the real job.

A usable chart has to survive contact with yarn, gauge and garment construction. Crochet stitches are not automatically square. A face that looks right on a digital grid can stretch on the finished piece. A design that looks correct in isolation can collide with a neckline or armhole. A palette that looks right on screen may not exist in the yarn colours I have.

03 · Strategy

Six principles kept the scope coherent.

Crochet-aware first

Gauge controls physical proportions. Hook size alone is not a reliable product input.

Manual correction is core

Automation output must stay editable. Human judgement is part of the workflow.

The garment is the context

Designs belong on real front, back, sleeve and custom panels, not only on an abstract square grid.

One source of truth

The pattern grid should power editing, instructions, production and export.

Local-first

Core production and client artwork should work locally before cloud dependencies are introduced.

Stage sophistication

Prove the single-user workflow before adding accounts, subscriptions, collaboration and SaaS complexity.

04 · MVP

Build the irreversible truths first.

The foundation focused on artwork import, measured gauge, gauge-corrected rows, colour reduction, an editable grid, palette control, basic manual editing, bottom-up written instructions, local autosave and project export.

Must work

Gauge correction, editable grid, reliable project state, instructions, local save.

Could wait

Yarn intelligence, business workflow, advanced exports, automation.

Explicitly deferred

Cloud accounts, subscriptions, teams and broad SaaS features.

Yarn became part of the product model.

Once a grid had to become a physical object, colour choices also had to connect to available yarn rather than exist only as screen colours.

06 · Key decisions

Three decisions changed the product model.

Decision 01

Gauge is geometry, not metadata.

The engine uses the actual stitch and row gauge from the swatch, plus source aspect, to calculate physical proportions.

Decision 02

One project owns multiple panels.

Front, back, sleeves and custom panels can carry independent design, palette, grid and production state.

Decision 03

Flat preview beat weak 3D.

The client needs a truthful approval view. Separate flat panels solved that job better than a low-quality simulated garment.

Before
Initial mental model: one chart represented the project.
After
Current model: project-level garment structure with independent panel state and cross-panel operations.
07 · Automation

Automation proposes. The maker remains in control.

Early background-removal approaches could remove the subject itself. The response was not to hide the failure behind stronger automation claims. The system moved toward conservative controls: background tolerance, edge and subject protection, smoothing, hole fill, largest-subject retention, dark-outline protection and semantic protect/remove/detail guidance.

The same pattern appears in candidate generation. Simplified, balanced and detailed recommendations can trade visual retention against crochet complexity, but the user can still edit the final grid.

08 · Quality

Some defects create physical rework.

Row orientation is a product-correctness issue. Body panels are worked bottom to top, so row 1 must map to the bottom edge of the chart. Sleeve construction can use a different direction, and the product needs to label that rather than forcing one convention everywhere.

Regression coverage

Gauge correction, crop behaviour, colour changes, grid editing, garment placement, yarn matching, production progress, exports, business calculations, multi-panel persistence and construction-aware counts.

Migration safety

Saved projects carry schema versions. New settings receive defaults while surviving user data is preserved across migrations.

09 · Business workflow

The job does not end when the chart is saved.

The current product can represent customers and orders, create a quote, track approval, material, payment and deadline states, and advance a job toward delivery. Client-facing quote output separates visible line items from internal pricing mechanics.

Product boundary

The app should own business workflow only where it needs to stay connected to design and production. It should not become a general accounting platform.

10 · Roadmap

Desktop before SaaS.

Now

Strengthen the desktop production workflow, use it on real orders, resolve reliability and usability gaps.

Next

External design-partner validation, onboarding, measurable workflow improvements and repeat use.

Later

Accounts, encrypted sync, subscriptions, teams, shared libraries, client links and analytics only after core workflow validation.

11 · Metrics

The next stage is validation, not feature volume.

  • Activation: project → gauge → pattern/freestyle → valid panel → production/export.
  • Time to production-ready panel compared with the maker's current workflow.
  • Manual correction burden by generated pattern and correction type.
  • Project save, migration and export success rates.
  • Repeat project creation within 30 days.
  • For business makers, quote-to-deposit conversion and lead-time visibility.
Important

This case study does not claim user growth, revenue, time savings or product-market fit that have not been measured yet.

12 · Reflection

What the project changed in how I think about product.

Domain expertise changes the questions.

Generic image tooling misses the constraints that determine whether the finished physical object is correct.

Recoverability matters.

Automation is more useful when users can inspect, correct and continue than when it pretends to be infallible.

Impressive is not the same as valuable.

Dropping a weak 3D direction in favour of flat approval views was a better product decision.

The construction-tech connection is real.

Both domains force software to respect geometry, sequencing, materials, dependencies and physical execution.
